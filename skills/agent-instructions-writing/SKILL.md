# AIが読んで従う文書を書くときの心得

## 共通の心得

### 読み手は賢いmodelである

文書を読んで実行するのは、文脈を読んで自分で判断できるmodelである。書くのは、modelが推論では到達できない事だけにする。プロジェクトや作者に固有の方針、隠れた制約、外からは見えない前提、やってみないと分からないgotchaがこれに当たる。

- 考えれば分かる判断を、防御的に明文化しない。edge caseの除外規定や、誤読を防ぐための但し書きを足さない
- 読解力の低いmodelに合わせて設計しない。文脈を読み取れないmodelは、文書が求める他の作業も実行できない
- 手順か例で目的が達成できるなら、背景説明を書かない。インシデントの話や、避けたい結果の説明がこれに当たる。gitの一般的な性質のように、考えれば分かる理由も書かない
- 比喩を書かない。読み手が比喩の別の側面を推論し、文の意味が曖昧になる

### 実行するmodelに向けた事だけを書く

その方法を選んだ経緯や、試して却下した案は、commit messageやPR概要欄に書く。

### 編集する時は、全体としての最善を目指す

既存の文書に手を入れる時、変更差分を小さく保とうとしない。足す内容を既存の節の末尾に継ぎ足すのではなく、その内容が最初からあったらどう書いたかを考える。構成を大きく変えて構わない。

### レビュー指摘の採否

外部Agentやsubagentの指摘は、事実として正しくても、文書に書く価値があるとは限らない。指摘が正しいかの検証とは別に、採否を以下の問いで決める。

- 問1. 賢いmodelなら、その場で判断できる事ではないか
- 問2. 対象の文書の種類に固有の心得が、書かないと定めた物ではないか
- 問3. 実行するmodelではなく、将来の編集者に向けた事ではないか
- 問4. それが無いと、modelが実行に行き詰まる事ではないか

問1から問3に当たる指摘は採用しない。問4に当たる指摘は採用する。

採用しなかった指摘は、理由を添えてユーザーに報告する。

## Agent Skill・カスタムagentの定義の心得

### 方針を書き、手段は任せる

何を確かめるか、何を達成するかを書く。どう行うかは、実行するmodelに任せる。

- どのツールのどのコマンドで行うかを、手順として指定しない。同じ操作でも、CLIで行う環境とMCPで行う環境がある。特定のコマンドを書くと、別の手段しか無い環境では成り立たなくなる
- 進め方が状況で分かれる作業に、特定のシナリオの具体例を入れない。modelが状況から判断するのをやめ、例に倣う

### 無いとmodelが行き詰まる記述は残す

「読み手は賢いmodelである」と「方針を書き、手段は任せる」は、具体的な記述を消す理由にならない。消す前に、その記述が無い時にmodelがどう実行するかを想像し、行き詰まるなら残す。

- 数万行あるlock fileから依存関係を調べる時の絞り込みコマンドのように、判断の助けになるヒントは残す。手順としての強制や、進め方を1つに寄せる具体例とは別の物である
- 特定のエコシステムに依存した記述を、抽象化のために先回りして消さない。他のエコシステムに対応する時に書き換えれば足りる

### 嘘になりうる事を書かない

- 外部ツールの出力の実例を貼らない。ツールの体裁が変わると実態と食い違う。何を抜き出すかは、報告や成果物の形式例で示す
- 外部の実装に由来する列挙値を書かない。相手の実装が変わると実態と食い違う。挙動の原理と大分類までを書く。例えばファイルの埋め込みを扱うskillなら、対応する拡張子の一覧ではなく、拡張子で判定される事と、画像・動画・音声という対象の大分類を書く
- 実行時に確定できない値を、記録項目や判断の条件にしない。推定値が混ざると、記録全体が信用できなくなる

## CLAUDE.md・AGENTS.mdのように、AIが作業の前に毎回読むルール文書の心得

### 制約を作業の一場面に限定しない

操作全体に効かせる制約を、「Zの後のXは指示を待つ」のように作業の一場面に限定しない。開発の流れは一様ではなく、特定の場面を前提にした規則は、その前提から外れた流れで噛み合わなくなる。

### 背景説明・理由を書かない

- 他所の文書から規則を取り込む時は、元に無い文を足さない
- 「〜しないと古くなる」のような理由を書かない。規則の効力を増やさず、逸脱した読み手への説教にしかならない
- 見出しや参照元で既に示したスコープを、冒頭で繰り返さない
- draftは仕上げている途中の状態、ready for reviewは人間にレビューを依頼できる状態、のような状態の定義は書いてよい。規則の意味を定める

### 同じrepoの中で、制約を2箇所に書かない

repoの中の制約は、毎回読まれるルール文書の1箇所に書く。そのルール文書と一緒に読まれる、そのrepoの中だけで使う手順の文書に、同じ制約を再掲しない。
