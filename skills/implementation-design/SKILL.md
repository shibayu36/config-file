# 実装の設計の文書

小規模な実装タスク1つについて、実装をどう作るかをユーザーと合意するための文書を書く。目的とやらないことは合意済みとして扱う。ポイントを押さえて合意し、細部は一度コードを作ってから調整する前提なので、合意に要る事だけを書く。

書く前と書いた後に core-message-writing skill に従う。想定読者はユーザーで、読後感は「各意思決定ポイントを判断して、設計に合意できる」である。

## 書かないもの

- コードを見てから判断した方が早い事。例えば関数名・変数名、ヘルパー関数の切り出し方、ログやエラーの文言。ただし、本番に出した後で変えにくい事（保存するキーの形式、APIの入出力の形など）は、小さくても意思決定ポイントにする
- 目的・やらないこと・背景の説明。それらが書かれた場所があればリンクする

## 構成

上から次の順に書く。

1. 冒頭: 何を作るかを1〜2行。目的とやらないことが書かれた場所へのリンク
2. 構成
3. 意思決定ポイント
4. テスト方針

### 構成

- 責務とそのつながりをMermaidのflowchartで描く。入口（APIのhandlerなど）から、今回の目的を満たすまでの流れを追える形にする。呼ぶ順番が設計の要点になる時は、sequence diagramも描く
- 置き場所の表: 置くもの（関数・型・定数など）とファイルパス
- この分け方にした理由。迷っている代替案があれば、それも
- 破綻条件: どんな変更が来たら、この分け方が成り立たなくなるか

図と表は、意思決定ポイントのおすすめを反映した形で描く。

### 意思決定ポイント

ユーザーと一緒に決めたい事を、大きいものから順に並べる。後から変えにくい事や、他の決定の前提になる事を先にする。1件はこの形で書く。

```markdown
### 1. <問いの形の見出し>【未決】

<判断に要る前提だけ。根拠のコードの場所を付ける。前の節で説明済みなら書かない>

- おすすめ: <値・シグネチャ・コード片などの具体的な形>
- 理由: <1〜2個。因果を飛ばさない>
- 迷っている代替案: <本当に迷っている案だけ。その案を採った時の帰結>
- 破綻条件: <どんな変更が来たら、おすすめが成り立たなくなるか>
```

複数案の検討は書く前に済ませ、文書には迷っている代替案だけを残す。迷っている案が無ければ、その行を書かない。

### テスト方針

テストする関数ごとに、テストケースを一覧にする。先頭には、その関数の仕様を最もよく表す正常系を置く。それ以外の順は問わない。fakeやmockにする依存があれば添える。

## 置き場所

保存先とファイル名は、プロジェクトの指示やユーザーの指定に従う。進捗ノートがあれば、その隣に置き、進捗ノートからリンクする。

## 合意した後

文書は常に最新の設計だけを持つ。

- 意思決定ポイントが決まったら【決定】に変え、おすすめを決まった内容に書き換え、迷っている代替案の行を消す。構成の図・表とテスト方針も、決まった形に書き換える
- 実装中に設計が変わった時も、同じように本文を書き換える
- 決めた経緯は進捗ノートに書く。進捗ノートが無ければ、【決定】の項目に理由と採らなかった案を1行ずつ残す
