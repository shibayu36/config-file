# 人が読みやすい単位に commit を分ける

作業ツリーにある変更を、レビューする人が commit ごとに意図を追える単位に分けて commit する。分けた後に、変更が 1 行も失われていないことを確かめる。

commit メッセージの書き方は、このスキルでは決めない。呼び出し元の指示とリポジトリの規約に従う。

## 1. 分け方を決める

`git status` と `git diff` で、未追跡のファイルも含めて変更をすべて読む。そのうえで、次の観点で commit の計画を立てる。

- 1 commit には 1 つの意図だけを入れる。1 つの意図が複数のファイルにまたがるなら、まとめて 1 commit にする
- 動きを変えない下準備の refactor は、動きを変える commit より前に分ける。変数名の整理のような小さなものは、本体と同じ commit に残してよい
- 機械的な変更（リネーム・フォーマット・生成ファイル・コード生成の結果）は、ロジックの変更と分ける
- コードの移動と、移動したコードの変更を分ける
- テストは、それが確かめる実装と同じ commit に入れる
- 並び順は依存する順を基本にする。読む順に並べたほうが分かりやすければ、並べ替えてよい
- 単独で読んで意味が分からない commit になるまでは細かくしない
- commit ごとに自動テストが通る必要はない

計画には、commit ごとに意図と、含める変更（ファイル、またはファイルの中の一部の変更）を書く。1 つのファイルを複数の commit に分けるときは、各 commit の時点でそのファイルがどういう中身になるかも決めておく。今回の作業と関係のない変更（もともとあった未追跡のファイルなど）は、計画から外しておく。

## 2. 分ける前の状態を残す

最後に比べるため、分ける前の作業ツリーを tree オブジェクトとして残す。

```bash
git add -A
git write-tree   # 出力された tree の hash を控える（以下 <snapshot>）
git reset -q
```

途中で状態が分からなくなったときは、`git checkout <snapshot> -- .` で分ける前の作業ツリーに戻せる。

## 3. commit ごとに stage して commit する

計画の順に、次を繰り返す。

1. 変更を stage する
   - ファイルの変更をすべてその commit に入れるときは、`git add <file>` で stage する。削除したファイルや移動元のファイルも、`git add <file>` で削除が stage される
   - ファイルの変更の一部だけを入れるときは、作業ツリーのファイルをその commit 時点の中身に書き換えてから `git add <file>` で stage する。書き換えた中身は、直前の commit 時点の中身（`git show HEAD:<path>` で取り出せる。移動したファイルなら移動元のパス、新しいファイルなら空）に、この commit で入れる変更だけを反映して作る
2. `git diff --cached --stat` で、stage したファイルが計画どおりかを確かめる。ファイルを書き換えて stage したときは、`git diff --cached` で中身も確かめ、計画にない変更や打ち間違いが入っていないことを見る
3. commit する
4. ファイルを書き換えたときは、書き換えたファイルをすべて `git restore --source=<snapshot> -- <file>...` で分ける前の中身に戻す

`git add -p` などの対話的な操作は使わない。

## 4. 変更が失われていないかを確かめる

すべて commit したら、次の 2 つを確かめる。

- `git diff --stat <snapshot> HEAD` に出るのが、計画から外した変更だけである
- `git status --short` に出るのが、計画から外した変更だけである

想定と違う差分が残ったときは、自分で直さずに、残った差分を報告する。commit 時の hook がファイルを書き換えたときも、ここで差分として出る。

## 5. 報告する

commit ごとに、hash・件名・含めたファイルを一覧にして報告する。
