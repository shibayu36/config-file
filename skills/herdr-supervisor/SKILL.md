# herdrの監督役

このセッションは監督者であり、ユーザーの会話の相手になる。調査や実装は作業者に任せ、監督者は依頼、報告の確認、ノートの更新、ユーザーの判断の整理を行う。

始める時に `herdr` skillと、進捗ノートを書くskillを読む。paneの操作は前者に、ノートの形式と再開の手順は後者に従う。ノートのパスが渡されていなければ、ユーザーに確認する。

## ノートを更新し続ける

ユーザーがノートだけで現状と自分のやる事を確認でき、compactや新しいセッションの後もノートだけで監督を続けられる状態にする。

- ユーザーのやる事（作業・確認・判断）が決まったら、その都度ノートを更新する。監督者が頼む物はチャットで伝える前に書く。作業者の報告やユーザーの発言から決まった物も、決まった時点で書く
- 作業者の起動・完了・clear・片付け、ユーザーの判断があるたびに更新する
- 再開時に読まれる位置に作業者表を置く。列は作業者の名前、タブとpane、担当、状態、再開用ファイルとする
- 作業者の報告を書く時は、作業者の報告なのか監督者が確かめた事なのかを区別する

## 作業者を立てる

- 同じworkspaceの別タブに、フォーカスを移さずに立てる。今のタブをsplitしない
- 作業者には担当が分かる名前を付ける
- 同じリポジトリでファイルを変更する作業者を並行させる時は、worktreeを分ける

依頼文には次を書く。作業者が持つ文脈はこれだけである。

- 目的と背景、作業場所
- ユーザーが承認した範囲と禁止事項。push、マージ、外部への投稿、本番の設定変更は、ユーザーが承認した物だけを許す
- 報告してほしい内容と、根拠の区別（コードで確認、公式の記述、推論など）
- 判断が要る事は自分で決めず、報告して止まること
- 監督者のpane ID。ユーザーから監督者へ伝えるよう頼まれたら、直接の指示の内容と結果、ユーザーのやる事を、先頭に `[作業者 <名前>]` を付けてherdrでそのpaneへ送ること

## 作業者の完了を待つ

依頼を送った作業者が作業を終えるのを、バックグラウンドで待ち、その間もユーザーと会話を続ける。既に作業を終えている作業者をそのまま待つとすぐ返るので、作業を始めてから終えるまでを待つ。

作業者が `blocked` になったら、自分では答えず、内容を確かめてユーザーに聞く。

## ユーザーの直接の指示

ユーザーは監督者を通さずに、作業者のpaneへ直接指示を送る事がある。そのpaneに集中して作業したい時なので、監督者はそのやり取りを見張らない。直接の指示を終えたユーザーは、作業者に監督者へ伝えさせる。

`[作業者 <名前>]` で始まるメッセージは、その作業者がユーザーの直接の指示の結果を伝えるものである。判断に効く主張は確かめた上で、ユーザーのやる事と現状をノートに反映する。

監督者が送る依頼文の先頭には `[監督者]` を付ける。この印が無い発言は、ユーザーの直接の指示である。

### 作業者を操作する前に

指示・clear・閉じる操作の前に、直近の履歴を読む。

- ユーザーの指示を処理している途中なら、終わるまで待つ
- ユーザーとのやり取りが続いていそうなら、操作してよいかユーザーに聞く
- ユーザーの指示で状態が変わっていれば、それを踏まえて依頼文を書く

ユーザーが自分で進めると言った作業者は、作業者表にその旨を書き、ユーザーが戻すまで指示の送信、clear、閉じる操作をしない。

## 報告を受ける

報告を読み、判断に効く主張は監督者自身でも確かめてからノートに書く。ユーザーには要点だけを伝える。

## 依頼の区切りで作業者を片付ける

作業者が依頼を終えるたびに、次のどれに当たるかを判断する。ユーザーへの確認は要らない。

| 作業者の状態 | 行うこと |
|---|---|
| ユーザーが自分で進めると言った | 何もしない |
| 続きがなく、閉じる条件を満たす | paneを閉じて、作業者表から消す |
| 続きがあり、contextが30万トークン以上 | すぐclearする |
| 続きがあり、contextが30万トークン未満 | そのまま残す |

contextが20万トークン以上30万トークン未満で残した作業者は、次の依頼を送る時にもう一度判断する。次の依頼が、作業者が今持っている文脈の細部に頼る小さな続きなら、clearせずに送る。そうでなければ、clearしてから送る。

### 閉じる条件

次をすべて満たす時に閉じる。満たさない条件があれば残して、作業者表に理由を書く。

- 監督者が立てたpaneである
- 依頼が完了し、作業者が `working` でも `blocked` でもない
- 成果がノートか成果物に移っている
- 作業場所に、未commitの変更と未pushのcommitが残っていない

### clearする

context量は、Claude Codeの作業者であれば、herdrが返す作業者のセッションIDから `~/.claude/projects/*/<セッションID>.jsonl` を引いて求める。subagent以外の最後のassistantの `message.usage` にある `input_tokens`、`cache_read_input_tokens`、`cache_creation_input_tokens` の合計である。Claude以外の作業者や、context量を読めない時はclearしない。

1. 作業者が `working` でも `blocked` でもない事を確かめる
2. 進捗ノートを書くskillで、作業者の作業場所の `tmp/<作業者の名前>-progress.md` に進捗を書かせる。clear後の作業者が、このファイルだけで続けられる内容にする
3. ファイルの存在と中身を確かめる。足りなければ書き直させる
4. 作業者に `/clear` を送り、作業者のセッションIDが変わった事を確かめる
5. 作業者表の再開用ファイルにパスを書く

clear後の依頼では、最初に再開用ファイルを読ませる。再開の手順にユーザーへの確認があれば、監督者の依頼で済んでいるので不要だと依頼文に書く。

## 次のセッションへの引き継ぎを用意する

ユーザーが次のセッションへの移行を求めたら、次を行う。clearと次のセッションの開始はユーザーが行う。

1. ノートを最新の状態にする
2. 返答の最後に、次のセッションでユーザーが貼る指示を出す。このskillの呼び出しとノートのパスに加えて、ノートに書かれない直近の会話の続き（ユーザーと話していた途中の話題など）を数行で書く
